# Memory Leaks: A World-Class Engineering Handbook

Memory leaks are not a language problem first. They are a **lifetime and ownership** problem.

In every runtime, a leak means the same thing at the system level:

- Memory remains allocated
- The program no longer needs the data
- But some ownership or reference path still prevents release

That is true in GC languages, in Rust, and in manually managed systems. The mechanisms differ, but the failure mode is consistent: **retention outlives usefulness**.

## 60-Second Summary (Core)

If you remember only five things:

1. A leak means memory is still retained after business value is gone.
2. In GC systems, reachable objects are kept alive even when no longer needed.
3. In Rust, ownership and `Drop` prevent many safety bugs, but logical leaks can still happen.
4. The most common production leaks are unbounded caches, forgotten listeners, and unpruned in-flight work.
5. Diagnose leaks by comparing memory snapshots over time and finding retaining paths.

## Runtime Model Comparison (Core)

| Model         | What frees memory                           | Common leak shape                                          | Main tradeoff                                                |
| ------------- | ------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------ |
| GC languages  | Tracing collector frees unreachable objects | Reachable-but-stale objects in caches, closures, listeners | Great ergonomics, but reachability != business need          |
| Rust          | Ownership + scope + `Drop`                  | Cycles (`Rc`), intentional leaks, unbounded collections    | Strong safety/perf, but requires ownership design discipline |
| Manual memory | Explicit free by programmer                 | Missing free, wrong owner, lifetime mismatch               | Maximum control, highest bug risk                            |

## Core Ideas (Core)

### Heap vs Stack

Stack memory:

- Function-local frames, return addresses, small fixed-size values
- Allocated and reclaimed by control flow (enter/return)
- Fast and deterministic lifetime

Heap memory:

- Dynamically sized or dynamically lived data
- Requires explicit strategy for reclamation (GC, ownership drops, manual free)
- More flexible, higher bookkeeping complexity

Practical truth:

- Most severe leaks involve heap retention, not stack growth
- Stack overflow is a different class (deep recursion / huge frame usage)

### Allocation vs Deallocation

Allocation answers: "Where do we place this data?"  
Deallocation answers: "When and by whose authority can it be reclaimed?"

If deallocation authority is ambiguous, memory pressure incidents are only a matter of time.

### Reachability

Reachability is the most important concept in GC systems:

- GC roots (globals, thread stacks, runtime handles, event loop structures)
- Object graph edges (references)
- Any object reachable from a root is considered live

Critical distinction:

- **Reachable** is a runtime property
- **Needed** is a business property

Leaks happen when these diverge.

## How Memory Flows (Core)

Memory flow should be modeled like a lifecycle pipeline:

1. Allocation request
2. Ownership assignment
3. Propagation through call graph / async boundaries
4. Retention while useful
5. Release trigger
6. Reclamation

When a system leaks, at least one stage has no robust invariant.

### GC Memory Flow

1. Object allocated on heap.
2. References propagate into app structures (cache, closure, queue, listener).
3. Runtime periodically traces from GC roots.
4. Unreachable objects are reclaimed.
5. Reachable objects remain.

A GC cannot reclaim reachable objects, even when logically stale.

### Rust Memory Flow

1. Allocation occurs via owned values (often heap-backed containers like `Vec`, `String`, `Box<T>`).
2. Ownership is unique unless explicitly shared.
3. Borrowing enforces read/write aliasing rules at compile time.
4. When owner goes out of scope, `Drop` runs deterministically.
5. Memory is released without a tracing GC.

Rust’s model eliminates broad classes of use-after-free and data races, but not all leak shapes.

![GC and Rust memory lifecycle comparison](/gc-vs-rust-memory-lifecycle.png "Side-by-side memory lifecycle: GC reachability tracing vs Rust ownership and Drop")
_Different lifetime control strategies, same engineering requirement: retained memory must match real business need._

## How Rust Solves Key Safety Issues (Core)

Rust is called memory safe because safe Rust prevents:

- Use-after-free
- Double free
- Iterator invalidation classes via aliasing violations
- Data races (in safe code)

Mechanisms:

- Ownership and move semantics
- Borrow checker (`&T`, `&mut T`)
- Lifetimes (compile-time validity constraints)
- `Drop` for deterministic cleanup
- `Send`/`Sync` trait boundaries for cross-thread safety

Why this matters for leaks:

- Default ownership paths naturally release memory when scope ends
- Lifetime errors surface at compile time instead of becoming latent production crashes

### Rust Leak Caveats

Rust can still leak memory in valid programs:

- `std::mem::forget`
- Reference cycles with `Rc<RefCell<T>>` without `Weak`
- Intentionally leaked singletons (`Box::leak`)
- Long-lived collections growing unbounded

Rust prevents memory unsafety by default, not all memory waste.

## Challenges With Garbage Collection (Advanced)

GC is excellent for ergonomics and safety, but operationally non-trivial.

### 1. Reachability Is Not Intent

If a stale object is still referenced by a cache, listener, task registry, or closure, GC must keep it.

### 2. Pause and Throughput Tradeoffs

Collectors balance:

- Pause time
- CPU overhead
- Heap footprint

Tuning one often affects the others.

### 3. Fragmentation and Promotion Dynamics

Generational collectors optimize common patterns, but long-lived accidental retention can push objects into old generations, increasing pressure and collection cost.

### 4. False Confidence

Teams sometimes assume "GC means no leaks."  
Reality: GC removes **unreachable** garbage, not semantically dead objects.

## Root Causes of Memory Leaks (Core)

- **Lifetime mismatch:** Object lifetime tied to process lifetime by mistake.
- **Unbounded retention structures:** Caches/maps/queues with no eviction or cap.
- **Forgotten deregistration:** Event listeners, observers, subscriptions never removed.
- **Timer/task capture:** Scheduled closures retain large graphs.
- **Detached-but-referenced resources:** UI nodes, buffers, handles still reachable via side tables.
- **Retry/backoff registries:** Failed work items retained indefinitely.
- **Accidental global references:** Debug references, module-level registries, singleton bags.
- **Async context retention:** Futures/promises keeping state machines alive longer than expected.

## Leak Patterns You Must Recognize (Core)

### Pattern 1: Linear Growth

What it is:

- Memory keeps increasing over time.

**Usually:**

- Cache retention without bounds
- Arrays/lists that only append
- Logs or buffers retained in memory

### Pattern 2: Step Growth

What it is:

- Memory jumps after specific actions.

**Usually:**

- Request-based leaks (per-request objects retained)
- Job queue leaks (completed/failed jobs never pruned)

### Pattern 3: Plateau (Healthy)

What it is:

- Memory grows and then stabilizes.

**NOT a leak:**

- This often indicates normal warm-up and steady-state retention

### Pattern 4: Unbounded Cache

How to detect:

- Heap grows with key cardinality
- No plateau under steady traffic

How to fix:

- LRU/LFU/TTL + max size + explicit invalidation on domain events

### Pattern 5: Listener Accumulation

How to detect:

- One event triggers increasing handler count over time
- Memory and CPU both rise

How to fix:

- Pair registration with deterministic cleanup
- Add scoped subscription helpers / RAII guards

### Pattern 6: Closure Retaining Large Object

How to detect:

- Timer/interval/task holds `bigData` through captured scope

How to fix:

- Capture minimal fields
- Break references after use
- Clear interval/timeouts on teardown

### Pattern 7: In-Flight Work Registry Never Pruned

How to detect:

- Map of requests/promises/jobs grows forever after timeouts/errors

How to fix:

- Always prune in success, error, and cancellation paths
- Add watchdog expiry sweeps

### Pattern 8: Reference Cycles

Common in shared ownership models.

How to fix:

- Make one edge weak (`Weak` in Rust, weak refs where available)
- Reconsider graph ownership design

### Pattern 9: Buffer Retention via Slices/Views

How to detect:

- Small view keeps large parent allocation alive

How to fix:

- Copy small needed region when retaining long-term
- Release or rotate backing buffers

## Observability & Detection (Core)

Leaks should be caught with telemetry before customer impact.

### Essential Signals

1. Process RSS trend
2. Heap used after full GC trend
3. Allocation rate vs reclamation rate
4. Old generation growth (GC languages)
5. Object count by key types/classes
6. In-flight queue/cache cardinalities
7. Container OOM kill frequency / restart reason
8. Latency correlation with GC pause metrics

### Healthy vs Leaking Profile

Healthy:

- Sawtooth pattern: rises with allocation bursts, drops after collection
- Long-term baseline roughly stable

Leaking:

- Post-collection floor trends upward continuously
- Memory never returns near earlier baseline

## Advanced Debugging Tools (Runtime-Specific)

Use runtime-appropriate tooling, but keep one invariant: compare snapshots over time and focus on retaining paths.

### JVM

- Java Flight Recorder (JFR)
- Eclipse MAT / `jmap` heap dumps
- GC logs + allocation profiling

### Node.js / V8

- Chrome DevTools heap snapshots
- `--inspect` allocation timeline
- `clinic heapprofiler`

### Go

- `pprof` heap profiles
- `runtime/metrics`
- `go tool pprof -diff_base`

### Rust / Native

- `valgrind` (where suitable)
- AddressSanitizer/LeakSanitizer
- `heaptrack`, `jemalloc` profiling
- `cargo-instruments` (platform dependent)

### Linux / Containers

- `smem`, `pmap`, `/proc/<pid>/smaps`
- cgroup memory metrics
- eBPF-based alloc profiling (advanced environments)

## Step-by-Step Debugging Strategy (Core)

![Memory leak debugging decision tree](/memory-debug-decision-tree.svg "Decision tree for validating leak shape, diffing snapshots, isolating retaining paths, and verifying fixes")
_Use this sequence in incidents to avoid premature fixes and to converge quickly on the true retaining path._

- **Reproduce growth deterministically:** Use fixed input load and duration.
- **Confirm leak shape:** Distinguish transient peak from rising post-GC baseline.
- **Identify growth domain:** Heap objects, native buffers, mmap, kernel/socket buffers, or fragmentation.
- **Capture time-separated snapshots:** Compare an early stable point vs a later inflated point.
- **Diff snapshots:** Prioritize dominators and retaining trees.
- **Trace to owning subsystem:** Cache, listener bus, task scheduler, transport, ORM, image pipeline.
- **Hypothesis and targeted patch:** Cap, release, weak reference, cleanup hook, or lifecycle correction.
- **Verify with same workload:** Ensure the post-fix memory floor stabilizes.
- **Add guardrail metrics/tests:** Make regression visible and testable.
- **Document incident pattern:** Add playbook entry and coding standard updates.

## Common Misconceptions (Core)

- **"GC means no leaks."** False. GC only collects unreachable memory.
- **"Rust cannot leak."** False. Rust avoids unsafe memory errors by default, but logical retention and cycles can leak.
- **"If memory drops sometimes, we’re fine."** Not always. Check post-collection floor trend.
- **"It’s a leak because RSS is high."** Maybe not. It could be allocator behavior, fragmentation, or intentionally retained arenas.
- **"Only long-running services leak."** False. Batch and CLI tools can leak too, especially in loops over large datasets.

## Prevention Techniques (Core)

### Architectural

1. Define ownership and lifetime contracts per subsystem.
2. Require bounded data structures on hot paths.
3. Treat cleanup as part of API design, not caller folklore.

### Code-Level

1. Prefer scope-bound resource management (RAII/defer/finally).
2. Avoid broad captures in async closures.
3. Use weak references for back-links in graphs.
4. Centralize listener registration with auto-dispose semantics.

### Operational

1. Alert on memory slope, not only absolute thresholds.
2. Track high-cardinality retainers (cache keys, in-flight maps).
3. Add canary load tests with memory assertions.

### Rust-Specific

1. Prefer `Arc<T>` + `Weak<T>` for cyclic graph edges.
2. Avoid `mem::forget` except for tightly justified FFI/lifetime bridging.
3. Review `static` and global caches for bounds.
4. Use drop guards for external resources.

### GC-Specific

1. Implement eviction policies by default for caches.
2. Remove listeners/subscriptions explicitly.
3. Avoid long-lived references from global registries unless justified.
4. Add periodic audits for "reachable but stale" structures.

## Real-World Scenarios (Core)

### Scenario A: API Gateway Cache Leak

Problem:

- Per-tenant response cache with no max entries.

Impact:

- Gradual old-gen growth, longer GC pauses, p99 latency degradation.

Fix:

- LRU + TTL + memory budget + per-tenant caps + cache hit/miss dashboards.

### Scenario B: Notification Worker Registry Leak

Problem:

- In-flight message map pruned only on success, not timeout/cancel.

Impact:

- Memory growth during provider instability.

Fix:

- `finally` cleanup + timeout cancellation path + stale sweep job.

### Scenario C: Rust Service Graph Cycle

Problem:

- Parent and child both held `Rc` strong refs.

Impact:

- Dropped request contexts never reclaimed.

Fix:

- Parent strong, child back-reference `Weak`; add leak test around lifecycle.

### Scenario D: Frontend Interval Capture

Problem:

- `setInterval` closure retained large historical state after navigation.

Impact:

- Browser tab memory climb and sluggishness.

Fix:

- Clear interval on unmount and avoid capturing full state tree.

## Mini Examples (Core)

### Reachability Example (GC)

```js
const cache = new Map(); // global root path
function remember(id, payload) {
  cache.set(id, payload); // payload stays reachable while key exists
}
```

If keys are never evicted, objects remain reachable and cannot be collected.

### Linear Growth Example (Leak vs Fix)

```js
// Leak: unbounded cache
const cache = new Map();
export function getUser(id) {
  if (cache.has(id)) return cache.get(id);
  const user = fetchUser(id);
  cache.set(id, user); // never evicted
  return user;
}
```

```js
// Fix: cap + TTL
const cache = new Map();
const MAX = 10_000;
const TTL_MS = 5 * 60 * 1000;

export function getUser(id) {
  const hit = cache.get(id);
  if (hit && Date.now() - hit.ts < TTL_MS) return hit.value;

  const value = fetchUser(id);
  cache.set(id, { value, ts: Date.now() });

  if (cache.size > MAX) {
    const oldestKey = cache.keys().next().value;
    cache.delete(oldestKey);
  }
  return value;
}
```

### Step Growth Example (Request Leak vs Fix)

```js
// Leak: in-flight requests retained on error path
const inflight = new Map();

async function handleRequest(id) {
  inflight.set(id, Date.now());
  const result = await riskyOperation(id); // throws sometimes
  inflight.delete(id); // not reached on throw
  return result;
}
```

```js
// Fix: always clean up with finally
const inflight = new Map();

async function handleRequest(id) {
  inflight.set(id, Date.now());
  try {
    return await riskyOperation(id);
  } finally {
    inflight.delete(id);
  }
}
```

### Rust Cycle Example

```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Node {
    parent: RefCell<Weak<Node>>,
    child: RefCell<Option<Rc<Node>>>,
}
```

Use `Weak` on one direction of the graph to avoid strong-reference cycles.

## Memory Leak Review Checklist

1. Is every long-lived collection bounded?
2. Are listener/subscription lifecycles symmetric?
3. Can async tasks be cancelled and cleaned up?
4. Do retries have terminal states and pruning?
5. Are cycles broken with weak references where needed?
6. Do snapshots confirm stable post-collection floor under steady load?
7. Do dashboards expose both usage level and growth slope?

## Final Engineering Takeaways

1. Memory leaks are ownership/lifetime design failures, not just coding mistakes.
2. Reachability is necessary for GC, but insufficient for correctness.
3. Rust reduces entire classes of memory safety bugs and improves lifetime clarity, yet still requires leak-aware design.
4. Prevention is cheaper than incident response: bounded structures, deterministic cleanup, and lifecycle contracts.
5. World-class teams treat memory as a first-class SLO dimension, with tooling, playbooks, and regression tests.

If you build from these principles, memory behavior becomes explainable, testable, and operationally reliable.
